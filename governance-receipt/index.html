Automata program · demo (b) · stratified Datalog with an exact count

A receipt for what
the agents did.

An AI agent spawns three helpers. Together they make about 190 tool calls on a codebase. Did any helper change a file it had never looked at? Did any write where it must not? This page shows the answer as a certificate: a count that someone who was not there can check.

every number on this page comes from a SYNTHETIC session:
a seeded generator, an invented project, no real transcript.

The generator, synth_transcript.py, writes two versions of one small session. In violating, one helper edits a file nobody had read and another writes to /etc/hosts. In fixed, the first reads the file before editing and the second writes inside the project.

The question.

A helper agent (a sub-agent) is allowed to edit a file only if it, or the agent that started it, had already read or written that file. An edit of a file neither of them had seen is a blind edit. A helper also must not write anywhere under six forbidden directories, a fixed list in the program. A violation is either one. The claim is the exact number of violations: 2 in the violating session, 0 in the fixed one.

"Zero" is the hard kind of answer. Showing one violation means pointing at it. Showing none means proving that nothing was left out. So the certificate carries a closure check: every fact the rules could derive is present. Without that check, a prover could report zero simply by not looking.

count(violation) = 0 is a statement about the committed log
and the rules, not about whoever computed it.

The rules.

The log becomes facts: one tool_call per call (with its own occurrence number, so two identical calls stay two), plus reads, writes, edits, spawned, next (consecutive steps of one agent), and the forbidden directories. Then two strata, with the negation reading only the first stratum's finished result:

written_path(P)      :- writes(W, P).
touched(R, P)        :- reads(R, P).
touched(R, P)        :- writes(R, P).
touch_upto(A, P, S)  :- touched(R, P), tool_call(R, A, T, S), written_path(P).
touch_upto(A, P, S2) :- touch_upto(A, P, S1), next(A, S1, S2).
prior_touch(W) :- edits(W, P), tool_call(W, A, T, S), next(A, S0, S),
                  touch_upto(A, P, S0).
prior_touch(W) :- edits(W, P), tool_call(W, A, T, S), spawned(A, Q, K),
                  next(Q, K0, K), touch_upto(Q, P, K0).
--- stratum 1 ---
blind_edit(W)      :- edits(W, P), tool_call(W, A, T, S), spawned(A, Q, K),
                      not prior_touch(W).
forbidden_write(W) :- writes(W, P), tool_call(W, A, T, S), spawned(A, Q, K),
                      prefix_of(P, X), forbidden_prefix(X).
violation(W) :- blind_edit(W).
violation(W) :- forbidden_write(W).

What gets checked.

The certificate is the facts plus a log of every rule firing, stratum by stratum. The checker is a Lean function extracted to a native program, datalog-check. It recomputes the hash root of the facts, replays every firing, and checks that each stratum is closed. Negated facts are read against the finished lower stratum, never a half-built one. Finally it compares the count. Lean proves that if the checker accepts, its database is exactly the standard stratified model of these rules over these facts. A second accepted certificate for the same rules and root could only claim a different count if the instantiated list hash collided. Reducing that to a SHAKE256 collision also needs the byte encoding to be injective, which is checked on examples, not proved.

Both certificates are accepted. The violating one is accepted at 2, because the certificate states the true count, whatever it is. Three forged certificates are refused on the fixed data. One leaves stratum 0 unfinished, so all 6 helper edits come out "blind" and it claims 6. Another claims the wrong count. A third deletes one fact but keeps the root. A weaker checker that tests closure only at the top stratum accepts the first forgery. That weaker checker's acceptance is why the per-stratum closure check exists.

The receipt.

checker=lake exe datalog-check (metatheory/DatalogCheck.lean)

It is signed with ssh-keygen -Y sign, under a demo key. The signature authenticates the text under that key. One command re-runs the checker for both certificates and compares the complete checked tuple—program, root, predicate and count—with each original signed receipt:

git clone https://github.com/emberian/dregg.git
cd dregg
demo/datalog-governance/run.sh verify

Requires Python 3, OpenSSH with ssh-keygen -Y, and the Lean toolchain selected by metatheory/lean-toolchain. The first run builds the checker. Run demo/datalog-governance/run.sh to regenerate both synthetic sessions and certificates, verify them against the original receipts, and run the three forgery checks. Outputs go to a fresh temporary directory; the trusted signer and published artifacts stay unchanged.

What this does not prove:

✗

anything succinct · checking is re-running the extracted checker natively, with no STARK and no proof system

✗

that the facts are a faithful reading of the session · the two short scripts that turn the log into facts are trusted, not proved

✗

anything about writes made through shell commands · only the structured file tools become facts

✗

that a requested call succeeded, or that two different strings are different files · facts are tool requests, and paths are compared as text

✗

order across agents beyond one rule · a parent's look counts only if it came before it started the helper

✗

the deployed hash · SHAKE256 with a domain prefix stands in for it, and its byte encoding is checked by test cases, not by a theorem

✗

that a helper never created a file without reading · that is allowed. The literal "read before every write" question flags every helper write, because they are creations, which is why the question counts edits

Why bother: agent swarms are going to touch real files, and "the logs look fine" is a feeling. A count with a closure leg, bound to a committed log and checked by a program whose meaning is a theorem, is a statement someone else can recheck without trusting whoever ran the agents or whoever counted.

Status, plainly: the Lean theorems (stratified negation, aggregates, closure by join, and the coincidence with the standard semantics for safe programs) are kernel-checked. The checker runs on both synthetic sessions shown here. Receipts are signed with a demo key. There is no proof-system leg yet.
