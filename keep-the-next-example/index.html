This prototype sorts software issues by learning from examples. Its memory stays encrypted while examples are added, old ones are removed, and questions are answered.

You can keep teaching it and restart it without losing the model. The latest version answers across eight categories in one encrypted calculation.

How the app works

The browser sends jobs to a local service. Closing the tab leaves the job running; restarting the service lets it continue from the last completed step.

1

Teach it.

Give it a text example and a category. The text encoder turns the example into numbers, which are encrypted and added to the model. A cryptographic proof checks the update before it is saved.

2

Ask a question.

The model compares the question with each category’s examples. The service checks the proofs for every category before decrypting the scores and returning an answer.

3

Keep teaching.

Each category remembers its eight most recent examples. When a ninth arrives, the oldest example’s encrypted contribution is subtracted and the new one is added.

Making the proofs faster

The encryption and the earlier proof system used different arithmetic. We built a new prover that works in the encryption’s own number system, avoiding the translation between them.

The new backend handles a complete memory update and the eleven stages of a linear similarity calculation. In the first full trial, it produced exactly the same encrypted outputs as the original implementation.

The model also uses a simpler score: average similarity instead of average squared similarity. Both versions gave the same aggregate accuracy on our small text test.

The two versions

The earlier two-category query took 1,103 seconds. The new one took 113 seconds. Both the scoring rule and the proof settings changed between versions.

Checking is still costly.

Computing the encrypted answer for one category took 0.37 seconds, while checking its proofs took 14.20 seconds. For a model this small, repeating the calculation is still cheaper than verifying the proof.

Technical details

The backend uses the four BFV fields directly, with an 8× low-degree extension, 64 FRI queries, quartic challenges and SHA-256 commitments. Its operands are public ciphertext coefficients. The numerical soundness bound for this profile is still being worked out.

A Lean theorem connects the FIFO update to all eleven linear stages. Proof extraction and the reconstruction of public inputs still need to be connected to the native implementation. Backend code and mathematics ↗

Eight categories
in one calculation

We then changed the way the encrypted memory is arranged. Instead of giving each category its own ciphertext, we fit eight category totals into one ciphertext. A query computes all eight scores together, dividing each total by its number of examples.

A separate nine-category test completed eighteen teachings, three queries and a restart in about 8 minutes 19 seconds. It also replaced two old examples. All the returned scores matched the direct calculation.

The first query covered eight categories in 88 seconds. Adding the ninth required a second encrypted batch; that query took 163 seconds. A fresh query after restart took 120 seconds and returned the same scores and ranking.

After that run, we used the browser to teach it a new network example and ask a new question. It answered network_transport, with all nine category scores matching the direct calculation. Teaching took 14 seconds and the query took 140 seconds.

Removing the master key

Today, the person holding the key can decrypt the whole memory.

The application checks proofs before it decrypts an answer. But the key also works outside the application, so its holder can bypass those checks. The text encoder runs outside encryption too.

Our goal is a system whose remaining keys allow learning and answering, without giving anyone unrestricted access to its internal state. That requires a different cryptographic construction around the working learner.
