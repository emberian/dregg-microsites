  89  ## 4. The profile: the served-path guard is no longer quadratic
  90
  91  `profile` sends the same shape of transfer at 64 KiB and at 256 KiB and
  92  reports the ratio, because a loaded box moves both measurements together:
  93
  94  - 65,536 octets: **0.106 s**
  95  - 262,144 octets: **0.146 s**
  96  - ratio **1.38** for a 4x transfer (bar: below 8x)
  97
  98  The guard `fn-tcl-drive` names is checked once per socket chunk by its ACL2
  99  executable counterpart. While it was `fn-tcl-sessionp`, that check walked
 100  every octet staged so far, so a 4x transfer meant 4x the chunks *and* 4x the
 101  walk -- about 16x the guard work. 1.38x is that cost gone; the residue below
 102  4x is the per-run process startup, which both measurements pay once. The
 103  `crash` scenario's 120,000-octet transfer, which w8 had to keep small for this
 104  reason, now takes 24 acknowledged segments without difficulty.
 105
 106  The covered scope: this is one box, one loopback, one segment MRU (4096) and
 107  one pair of sizes. It is a refutation of a quadratic guard, not a throughput
 108  number, and the send direction is still quadratic (`specs/tcpcl.md` §6).

 110  ## 5. A finding: the model differential is only sound for a receive-only session
 111
 112  The first run of the lab -- the first run there has ever been -- failed
 113  `replay` at

 115  ```
 116  '(:OUTBOUND-SENT 0 "passive")' != '(:SEND :MSG-REJECT 3)'
 117  ```
 118
 119  `tcpcl replay` folds `fn-tcl-drive` over the trace and calls nothing else, so
 120  it models a node that consumes octets and never originates a transfer. A node
 121  that also sends reaches `fn-tcl-send` and `fn-tcl-pump` from the *host*, not
 122  from the wire; the replay's state has no outbound transfer when the peer's
 123  XFER_ACK arrives, and the machine is right to answer MSG_REJECT Unexpected
 124  where the loop said `:outbound-sent`. `exchange`'s listener carries a reply
 125  bundle, so its trace was never a valid subject for this differential.

 128  receive-only listener and the differential holds exactly (9 loop events, 9

  18

  39  ## What did not run, and why
  40
  41  No receipt was returned over BP. ION gives the sending application no bundle
  42  identifier — `bpsendfile` prints none and `bp_send()` returns only an in-process
  43  `SdrObject` address — so fn's durable attempt record has no observed transport
  44  handle to bind. The return leg is blocked behind that seam rather than faked.
  45
  46  ## The receive seam
  47
  48  **ION has no non-destructive receive.** `bp_receive()` deletes the endpoint's
  49  delivery-queue element, zeroes `bundle.payload.content`, destroys the bundle and
  50  commits the SDR transaction *before it returns*. Afterwards nothing redelivers
  51  the ADU, and `bp_release_delivery(&dlv, 0)` only leaks the ZCO without making it
  52  reachable through any endpoint API. `bprecvfile` compounds this: it writes
  53  `testfile<N>` with no `fsync`, no rename into place, and a per-process counter
  54  that restarts at 1, so a restarted receiver silently overwrites earlier files.
  55  Neither is restart-safe in fn's sense.
  56
  57  `tests/ltp/fn_ltp_stage.c` is the app-level staging copy this forces: take
  58  delivery, write the exact ADU to a temporary file, `fsync`, rename into the
  59  staging directory under the RFC 9171 bundle id, `fsync` the directory, then
  60  release. `IonStagingInbox` serves fn's `inventory`/`download`/`delete` from that
  61  copy, so `delete` removes fn's own staged file, never an ION-retained bundle.
  62  The window between `bp_receive()`'s commit and the staging `fsync` cannot be
  63  closed with ION's public API; it is covered at the fn layer by durable sender
  64  work, retry and receipt idempotence, not by the BPA.
  65
  66  ## Delegated behavior and its limits
  67
  68  ION owns LTP session establishment, 1,200-octet red-part segmentation,
  69  checkpoints, reception reports, retransmission, bundle lifetime expiry, and BP
  70  forwarding over the contact/range plan. Its repair is budgeted: `maxTimeouts 5`
  71  and `maxRepairRounds 8` per session. An outage longer than that budget cancels
  72  the session, and BPv7 has no custody transfer to recover it, so recovery falls
  73  back to fn's own durable retry. `sessionInactivityLimit` was 0 and one-way light
  74  time was 0 in this profile.
  75
  76  ## What this is not
  77
  78  Not interoperability qualification: one implementation, one host, one profile,
  79  no cross-implementation vectors and no errata audit. Not a mission profile: IPv4
  80  loopback UDP, zero light time, no contact plan, no asymmetry, no rate limiting.
  81  No BPSec, no authenticated peer, no author signature; the A_POLICY premise is an
  82  explicitly trusted local test input. No power-loss or physical-media
  83  qualification. No relay topology, backpressure campaign or staging-quota
  84  exhaustion. LTP reliability is not fn application acceptance, and none of these
  85  results closes `REP-006` or `SCN-010/017`.

   9  ## Assurance grows with the implemented surface
  10
  11  Each new reachable command, persistent record, transition, codec or adapter
  12  operation adds assurance obligations. A proof about an older component does not
  13  automatically cover a new caller or the composition between components. Keep
  14  three things distinct in the [closure inventory](../planning/assurance-closure.md):
  15  evidence for implemented behavior, missing evidence for implemented behavior,
  16  and requirements for features that have not been implemented.
  17
  18  For each behavior-changing batch, record the affected stable requirement/proof/
  19  scenario IDs and the following change in scope:
  20
  21  | Changed surface | Evidence to add or explicitly leave open |
  22  | --- | --- |
  23  | State or transition | Meaningful initial/reachable invariant, rejection behavior, preservation of prior accepted facts, and finite traces |
  24  | Caller or composition | Relation to the actual callee's state and hypotheses, including pending work; shape validity alone is insufficient |
  25  | Durable record or side effect | Byte/record correspondence, barriers and uncertainty, live-versus-replay agreement, restart and lost-completion cuts |
  26  | External bytes or raw execution | Decoder domain/canonicality, limits and work, guard status of the executed call graph |
  27  | Authority or release | Exact evidence/context binding, durable decision, explicit policy/crypto/peer premises, preservation of independent obligations |
  28  | Transport or scheduling | Duplicate/reorder/expiry/contact behavior; safety and conditional progress stated separately |
  29
  30  A feature checkpoint may remain experimental with an exact open list. It does
  31  not count as assurance closure until its applicable claims have evidence.
  32  Changing a profile or a trust assumption to avoid an obligation changes the
  33  contract and must be recorded as such. Keep critical missing composition/recovery
  34  evidence in a bounded closure batch before building dependent behavior on it.
  35
  36  No count appears in this document. Theorem, root, guard and test counts live
  37  in [the generated ledger](../planning/ledger.md) and nowhere else, because a
  38  number that is typed is a number that drifts. Prose carries the property, its
  39  hypotheses and its covered scope in one sentence; it does not carry counts.
  40  Report the property, supported domain, source digest and assumptions. A growing
  41  count does not demonstrate that the assurance gap is shrinking. Review the
  42  frozen batch once, fix concrete defects, and keep independent work moving; this
  43  discipline adds no approval ceremony.
  44
  45  ## Refinement ladder
  46
  47  1. **Abstract executable state:** finite maps/records and event transitions.
  48     Prove recognizer preservation, identity/allocation invariants, and phase rules.
  49  2. **Bounded bytes:** refine external parsing/encoding to the accepted object and
  50     NNTP domains. Prove decoding, deterministic preimages, and framing properties.
  51  3. **Crash storage model:** relate logical acceptance to records, writes, barriers,
  52     recovery, and checkpoint selection under named platform assumptions.
  53  4. **Concrete execution:** use guard verification and explicit correspondence
  54     between logical maps and efficient representations, including abstract stobjs
  55     where useful. Include range-query completeness in index obligations.
  56  5. **Multiple nodes:** reason about validated fact sets, obligation transitions,
  57     duplicate/reordered exchange, and explicitly conditional progress properties.
  58
  59  The program used by the host must be these definitions or a justified refinement.
  60  An abstract model plus an independently written server is insufficient evidence
  61  for claims about the running server.
  62
  63  ## Shape of the claims
  64
  65  State preservation has the schematic form
  66  `inv(s) and permitted-event(s,e) => inv(next(s,e))`. Prefer total, guarded
  67  interfaces that explicitly reject malformed events rather than assume away
  68  untrusted wire inputs. An invariant must include meaningful initial states and
  69  reachable examples, so a theorem is not satisfied by an empty state domain.
  70
  71  Trace induction lifts one-step safety properties to finite executions. Eventual
  72  delivery additionally needs a scheduling/contact/resource model and A-FAIRNESS.
