01 / What the service owes

The letter outlives the connection.

“Accepted”
is a promise.

A post is more than bytes arriving at a socket. fn intends to preserve exact content, commit its group allocations together, and retain it until an authorized release. A disconnected sender must be able to return without inventing a second transaction.

The important states are accepted, refused, and uncertain. An error can happen after the disk has changed. A reply can disappear after the server has committed. Storage contract ↗

04 / What the review caught

Neither greenwashing nor archaeology.

Read the joins.
Then the claims.

The docs can get ahead of the runtime. They can also lag behind repairs. Source, evidence and revision have to travel together.

01“The digest is in ACL2” is only partly integrated.

Content identities now reach executable ACL2 SHA-256. But frame sealing still calls Python's hashlib.sha256 and the native host's fnn-sha256. The architecture's broad trust-boundary claim is ahead of those call sites.

Attaching an implementation proves it meets the seam's constraints. Here those are shape constraints. Vector tests and guard verification do not establish full standards equivalence or cryptographic security.

The attachment · Python frame sealing · Native frame sealing
02Auth books and a TLS listener do not yet make authenticated posting.

The proposed stored-secret verifier is not called by AUTHINFO. The existing comparison is still against the clear secret; the served fold has not adopted the auth wrapper. Implicit TLS and principal authorization are separate boundaries.

Before wiring the new scheme, choose the credential profile: fast salted SHA-256 is not an expensive password hash for human-chosen passwords. A shape theorem about a verifier record does not establish secrecy. NIST password guidance distinguishes salt and computational cost.

03The statement CLI still verifies with toy crypto.

It explicitly loads the toy crypto test book and labels its verdict non-cryptographic. Its Ed25519 option emits a real signature separately, marked “not attached.” This is honestly labeled experimental machinery; it is not yet the deployed native-signature workflow.

The new campaign constrains recovered record counts using a namespace envelope. It does not check exact recovered record octets, enumerate torn fragments or yet demonstrate failure against a deliberately unsafe host. The byte scanner/refinement is still absent.

Local transcription checking reports missing host cuts and explicitly unmodeled boundaries. “Zero fidelity defects” is one category in that output, not a claim that every cut is covered. A process kill is also not a power loss.

05 / What assurance means

A claim with its reasons attached.

Can we account
for the whole promise?

For this use, assurance is a justified claim about a particular implementation under stated assumptions. A theorem count cannot tell you whether the missing connection is the one that loses your letter.

  1. 01User claimWhat does “accepted” mean?
  2. 02Exact theoremProperty + hypotheses
  3. 03Called codeThe running subject
  4. 04I/O relationBytes, barriers, recovery
  5. 05Operating evidenceFaults, peers, platform

Safety

No wrong completion, duplicate allocation, partial cross-post or unauthorized release. State the bad event the proof excludes.

Recovery

Every accepted obligation survives each permitted crash. Show that the actual loader sees a permitted image.

Authority

Who signed which bytes under which policy? Preserve contradictory evidence without giving it authority.

Availability

Bound hostile input and work. Keep readers usable as the archive grows. Safety alone does not imply eventual delivery.

Operations

Install, upgrade, back up and recover one reproducible build. Refuse new promises when capacity cannot support them.

Meaning

A transport ACK, application receipt, valid signature and human reading are different events. Let the interface say which happened.

BP delivery to an application agent does not establish payload processing: RFC 9171 §5.7. fn's retained-content receipt is a stronger application contract.

06 / Why build this at all?

Shared memory.
Explicit obligations.

A human returning next week and an agent restarting without context should be able to find the same accepted letter.

That is the useful foundation fn is working toward: stable content, recoverable work, inspectable provenance, and a record of disagreements that survives a relay. It could support communication without requiring everyone to be awake, connected or using the same client.

A signature does not make a message true, benign, or authorized to invoke an agent's tools. Those permissions belong at the application boundary. Nor does this work establish private-group confidentiality.

↗

The space-age idea is a durable obligation.

Let an expired carrier die without forgetting the work it carried. The LTP and TCPCL experiments make disconnected operation more concrete. Extraterrestrial use still needs a mission profile: contact and clock uncertainty, asymmetry, resources, autonomous recovery, and qualified hardware. No flight-readiness claim follows from these labs.

07 / The next substantial step

Finish coherent paths in batches.

Close a route.
Earn its claim.

  1. A

    Serve one complete promise.

    One integrated owner build: real-client POST, concurrent reader, lost reply, recovery and idempotent retry. Certify the code that image runs.

  2. B

    Close the survival relation.

    Byte scanner and refinement, exact recovered content, both directions of the cut map, an unsafe-host control that demonstrably fails, then a qualified barrier profile.

  3. C

    Carry the promise between nodes.

    Join acceptance to the durable feed; finish native BP/node/receipt integration. Outages and carrier expiry must preserve work without duplicating its effect.

  4. D

    Make authority independently checkable.

    A real signed artifact, independent verification, durable verdict and policy context, and authentication connected to the served path.

The ambition is sound. The valuable next increment is a complete, inspectable chain of reasons to trust a promise.
