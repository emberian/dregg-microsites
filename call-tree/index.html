dregg microsites 18 · Call trees

Initiative 9 · attested transport + receipts

The call tree,
certified

An agent asked a model a question. The model asked for a tool. The tool fetched a page. The model answered. Each of those four HTTPS exchanges was witnessed by a notary while it happened, and the whole tree is one 256-bit root that a stranger checks offline in a tenth of a second.

The tree that happened

turn kind 0 · root afd03350…8d4a76 ├─ POST api.z.ai /api/coding/paas/v4/chat/completions kind 1 · glm-5.3-flash · 7.7 s │ asks for fetch_page("https://example.com/") ├─ POST tool.calltree.invalid /fetch kind 2 · 6.5 s │ │ returns a span of the page and "subtree_root":"…" │ └─ GET example.com / kind 1 · fetched by the tool, through its own attested hop · 3.3 s └─ POST api.z.ai … kind 1 · 5.4 s "This page exists as a domain reserved for use in documentation examples, without needing permission." edge 0 "https://example.com/" model response → tool request edge 1 "This domain is for use in docum…" page response → tool response (child → parent) edge 0 the same span tool response → model's second request

Every hop is a TLSNotary MPC-TLS session (tlsn alpha.15): the prover and a separate notary jointly ran the TLS client, so the notary never saw the plaintext and the prover could not have forged the server's bytes without the notary's key share. The Authorization header's value is hidden in both model presentations; the key appears nowhere in the record. The tool server records its own outbound fetch the same way and returns the root of that subtree inside its attested response, so the agent's attestation of the tool call binds what the tool says it did.

What the checker decides

The verifier binary runs presentation.verify() on each hop and passes on only what it authenticated. Everything else is a Lean function, CallTreeDeploy.deployedVerify, compiled and run as calltree-check:

The theorems. commit_binds_or_collides: two trees with one root are equal, or a total extractor names the two inputs on which the hash collides, and deployed_coll_is_blake3_coll shows that pair is a BLAKE3-256 collision on distinct messages. verify_sound and no_omission: an accepted tree is the committed one, every node with exactly its children, none dropped, added or reordered. verify_attested: every non-root node is a transport hop, attested, given the named carrier that a verified presentation means what TLSNotary says it means.

Re-verify it yourself

# breadstuffs (github.com/emberian/dregg), offline after the build
calltree/verify/run.sh
# = lake build calltree-check; cargo build calltree/verify; then
dregg-calltree-verify --recording calltree/fixtures/glm.recording.json \
  --policy calltree/fixtures/glm.policy.json \
  --root afd0335078e2d1ec0e13ea6cc6be2e20df7695d20559ffdc7c782ba12e8d4a76 \
  --extra-root tool.calltree.invalid=calltree/fixtures/tool-root.der \
  --checker metatheory/.lake/build/bin/calltree-check
verdict ACCEPT · extract 7 ms · Lean check 92 ms
fresh sparse clone + build + verify on a 32-core box: 19 s + 57 s

Ten tamperings of the real recording are refused, each by the check you would expect: a dropped child, reordered children, the tool relabelled as a plain hop, its subtree dropped, one flipped byte or one trailing byte in a presentation, an edge made of header boilerplate or of masked bytes, a missing required edge, and a different trusted root.

ACCEPT means: under the notary key you pinned, these four TLS sessions happened with these hosts and carried these bytes; the tree is exactly the committed one; and the bytes the model asked for, the page returned and the model was then shown match across the hops. It does not mean the agent made no other calls.
✗

the notary's honesty · MPC-TLS needs the notary not to collude with the prover. Here both are ember's (one box, separate processes); a stranger who wants independence pins an independent notary's key, and the recording names its operator

✗

completeness · a recorder that makes a call outside the tree leaves no trace; non-omission is about the committed tree, and dataflow edges bound only what a bypass could hide from the model

✗

the root's origin · you trust the root you pass on the command line. The grain turn it was minted into is shown, but that cell comes from the host that ran the executor, so it is reported, not counted

✗

the tool's identity · the tool server has no public name; its self-signed root is pinned per host, and it can only vouch for that host

✗

meaning · edges are byte spans of at least 16 bytes in request and response bodies, not typed JSON fields keyed by tool-call id (next)

✗

freshness · the policy bounds the notary's time window; there is no verifier challenge yet

Why bother: a zkTLS proof per call says each call happened. A certified tree also says these were all of the calls in this turn, in this order, under these parents, and that what the model saw is what the tool's page said.

Status, plainly: the general theorems are kernel-checked; concrete falsifiers are compiled evaluation; two cross-model audits adjudicated in calltree/GROUNDING.md. One real tree, one notary operator, a self-signed tool. Publication is a separate step.
