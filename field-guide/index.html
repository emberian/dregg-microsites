Dragon’s Egg / a proof-native computer

Computing that

Dregg is building a shared computing world where agents have explicit powers, operations have mathematical rules, and participants can check the evidence.[1]

The central idea

Specify what an operation must mean. Let implementations find the evidence. Check that evidence before relying on the result. Dregg connects this approach to authority, private data, and shared state.[5]

01 / Five ideas

What makes this
worth paying attention to.

Five concrete ways the architecture changes the relationship between a participant, an operation, and the software performing it.

01
Authority

Give agents powers. Not the keys to everything.

An agent should be able to do useful work without inheriting unrestricted access to your resources. Dregg uses explicit capabilities: the system checks what an action is allowed to touch, and delegated authority can become narrower, not larger.

The decision to act comes from the model. Admission comes from the capability and execution layers. That makes permission a system boundary rather than a request in a prompt.[2][3]

Why it matters

Useful delegation without making the model’s judgment the security boundary.

02
Execution

The verified core is part of what actually runs.

The native execution path uses the Lean executor’s resulting state. The proving architecture also consumes Lean-authored constraint descriptions. The connection to formal methods is in the execution and proof machinery, not only in an accompanying specification.

This is a source-level architectural fact, not a claim that the entire compiler, host, and deployed binary have been proved correct. Those correspondence boundaries still matter.[4][8][14]

Why it matters

Connect mathematical guarantees to the software that performs the operation.

03
Computation

Prove the rule. Not every step of the search.

A market, parser, game, or policy can retain its own semantic relation and specialized proof. The common interface is a proof-bearing receipt, rather than a requirement that every operation first become the same virtual machine’s instruction trace.

Where a suitable compact certificate exists, checking the result can avoid reproducing the search that found it. This is a design opportunity—not a universal performance guarantee.[5][16]

Why it matters

Choose the machinery that finds the answer. Keep the acceptance rule fixed.

04
Privacy

Private inputs. Independently checkable outcomes.

Bounded implementations demonstrate private-book clearing and legal moves from committed hidden hands. A verifier can check the permitted result without receiving all the inputs used to establish it.

That privacy is from proof consumers. A process building the proof may still see the witness; removing every single viewer requires additional distributed cryptography.[7][11][21]

Why it matters

Reveal the fact that matters without automatically revealing the data behind it.

05
Worlds

One shared world. More than one way to inhabit it.

Cells, authority, state changes, and receipts form a common foundation for applications and agents. DEOS presents those objects through different views while retaining their underlying rules and history.

Recursive receipts support succinct history verification under the stated proof-system assumptions. The pieces are implemented to differing degrees; a polished, unified public environment is still ahead.[9][10][12]

Why it matters

Let interfaces change without making each interface the owner of the world.

02 / Under the surface

How the pieces fit.

The details behind the headlines: what the proofs say, how they connect, and where the boundary still lies.

Two kinds of correctnessA receipt that can composeCheck the certificateAuthority, not alignmentOne private-market exampleObjects beyond their UI

Two questions. One architectural connection.

Formal verification

Does the program obey the intended rules?

Reason about the program and its relationship to a specification.

Proof of computation

Did this claimed operation satisfy those rules?

Check evidence for this particular input, result, and state change.

Dregg connects these questions through its native execution and proving paths. The native executor module describes produce_via_lean installing the Lean-produced post-state. In the formal source, the gated-forest development includes exact asset conservation and conditions for credential validity, capability authority, discharged caveats, and revocation.[3][4]

The private-market proof module supplies a concrete example of the other half: Rust validates inputs and builds the witness, then consumes a descriptor emitted from Lean. The following path is included directly by the implementation.[8]

include_str!(
  "../../circuit/descriptors/by-name/dark-bazaar-private-n4k4.json"
)

This expression shows artifact consumption, not complete end-to-end compiler verification. The full implementation is linked in source 8.

Lean-authored, proved against a specification, and automatically compiler-derived are different properties. The compiler assessment records that distinction and the remaining semantic work. The architecture makes these connections explicit; it does not make them automatic.[15]

The common interface is an accountable step.

A proof can be valid and still concern the wrong operation. Dregg’s receipt design therefore binds program identity, verification-key identity, the state before and after, the deliberately public result, and the step’s place in a history. Continuity requires adjacent state commitments and step indices to agree.[6]

Different kinds of operation can meet at this boundary without using the same internal algorithm. Recursive aggregation then supports a compact check of linked history rather than full replay. That history claim remains conditional on the named recursion and FRI proof-engine assumptions.[6][12]

Do not merely ask whether a proof verifies. Ask whether it proves the exact operation you meant to authorize.

Sometimes the search is not the thing to prove.

Consider an optimizer that works hard to find a result. A suitable certificate can justify the answer without narrating all that search. DrEX applies this pattern to market clearing: its certificate checks cover constraints such as admission, limits, conservation, and the objective gap. The documented scope is a developer instance, not a public real-money exchange.[16]

This is not a claim that other zkVMs cannot check certificates. A zkVM can run a certificate verifier, and systems such as RISC Zero already bind public results to an expected program identity. Dregg’s particular emphasis is making heterogeneous semantic relations and their composition into authorized state changes central to the architecture.[5][18]

Nor do recursive proofs erase the original proving cost. The benefit depends on the relation, the certificate, and the implementation; there is no universal speedup hiding in the word “semantic.”

Permission should not depend on persuasion.

Imagine giving an agent access to one bounded resource pool and a limited class of operations. Its model can propose actions, but the surrounding system checks whether those actions fall within the granted authority. This is an illustrative use of dregg’s capability model—not a claim that any arbitrary natural-language policy is already enforced.[2][3]

The agent platform describes confined tools, lifecycle and budget machinery, and receipts bound to real kernel turns. These mechanisms address what an agent can do. They do not certify whether its plan is wise or whether the user selected a good policy.[2]

An authorized action can still be a bad idea. Bounded authority limits the consequences; it does not manufacture judgment.

The broader model is not only about owners controlling agents. Cells have state and installed rules, with capability-governed interactions between participants. The same architecture is meant to support boundaries for agents as well as boundaries around them. That is not a guarantee against every host or hardware compromise.[1][9][14]

A tiny market with a precise privacy claim.

The documented Dark Bazaar private relation accepts at most four orders over four price buckets, with quantities from 0 to 15. It commits to the private book and proves a public clearing price and crossed volume, including the specified lowest-price tie-break among volume-maximizing choices.[7]

Kept from the verifier

The underlying order book.

The hiding proof need not expose the individual private orders.

Made checkable

The bounded clearing result.

The price and volume are checked against the committed book and stated relation.

The trace-building process still receives the plaintext witness. This fixed relation also does not, by itself, authenticate incoming orders, assign all individual fills, or bind them into ledger settlement. Those are separate obligations. Privacy from consumers is not the same as privacy from every service involved.[7][8][21]

Games give a less financial illustration: a committed hidden hand can support proof of a legal card play without publishing every card. The same distinction applies—checkable rules and selective disclosure, not a blanket promise that the entire application leaks nothing.[11]

An interface can be a view, not an owner.

DEOS renders cells and their available actions. A button proposes a transition; an inspector reveals authority and provenance. The shared view model supports different presentation surfaces, while the underlying object remains governed by its own state and rules.[10]

The project documents replay, forks, and constrained branch settlement. Its network adds history selection and succinct verification; it does not eliminate the need for a finality rule. Neither those mechanisms nor public development viewers establish a stable production mainnet.[10][12]

The long-term possibility: people and agents using different tools to act in the same inspectable world.

That is an architectural direction, not a claim that the desktop, agent host, games, and network already ship as one finished public service.[9][13]

03 / Research status

Strong ideas.
Explicit boundaries.

Read the claim at the level it is actually supported: a theorem, an implementation, and a public product are not interchangeable.

Formal and implementation evidence

More than a proposal.

The record contains machine-checked components and running proof and execution paths. The native Lean executor and bounded private-market implementation are concrete examples.[3][4][8]

Still conditional

Assumptions remain visible.

Cryptographic soundness, correct statements, and correspondence to deployed software still matter. Whole-history verification is wired, but its strongest guarantee remains conditional.[12][14]

Product and security boundary

Not a finished platform.

The integrated system has not had an independent external audit and is not ready for security-critical use. A unified, generally available public environment is still unfinished.[13]

A clean proof is not enough if its premise is wrong. The assurance source explicitly records earlier injectivity-shaped cryptographic premises that were refuted, why they created vacuity, and the work to replace them with appropriately scoped games or random-oracle statements. Checking the proof’s axiom footprint does not establish that its hypotheses are satisfiable.[14]

Integration, not an invented lineage. Capabilities, formally verified kernels, and execution receipts have prior art in systems such as Agoric, seL4, and RISC Zero. The case for dregg is its particular combination and the operations being built with it—not a claim to have invented every ingredient.[18][19][20]

The software and the token are separate claims. The project’s token page states that $DREGG has no current in-protocol function and describes service payments as future use. This page describes computing architecture, not token returns, value accrual, or existing protocol demand.[17]
