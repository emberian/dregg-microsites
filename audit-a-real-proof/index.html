Initiative 8 · commit-then-audit over FlashProve

Audit a
real proof.

A provider serves answers and claims each one is its committed model's. Checking every proof is expensive, so you check a few, chosen by a coin nobody could see when the answer was committed. How many lies get through before the first alarm? A theorem says at most about 1/p on average. This page shows that number measured on FlashProve's real verifier, and one receipt you can check yourself.

the proofs here are FlashProve's two stored exact-match proofs, made with synthetic weights. We have no H100, so the audited population is replays of those proofs, and the corrupt answers are false claims made from them. Every audit that fired is a real cp_verify call.

The loop, in order

1. Commit. Each answer becomes a record: the hashes of the request, the answer token and the proof, the pinned model ID, and the latest drand round the requester has seen. The record goes into an append-only Merkle mountain range, and the requester signs the position, the record, the root and that round.

2. Coin. The audit coin comes from drand round seen + 2. That round did not exist when the requester signed. The coin is a hash of the round's BLS signature, the session and the position.

3. Decide. Three questions are answered by Lean code compiled into the auditor: did the audit fire? What did the verifier say? Is there an alarm? It is the same code the Lean instance of the theorem is built from. Rust only moves bytes.

4. Fail closed. A fired audit alarms on anything except an accepted proof of the committed answer. That includes a rejection, a missing proof, a timeout, a crash, files that don't match the record, and output that doesn't parse.

The falsifiers show the theorem's hypotheses are needed. If "no verdict" counts as no alarm, a provider that just withholds its proofs is never caught. If the provider can commit after it sees the coin, it lies only when no audit will fire.

Re-verify it yourself

# the auditor (breadstuffs audit-flashprove), built against minidregg's Lean
MINIDREGG_DIR=../minidregg cargo build --release -p audit-flashprove
# offline: MMR opening, countersignature, round rule, BLS, coin, decision
fpaudit recheck --pins pins.json receipt-*.json
# acceptance evidence: re-run cp_verify on the committed files
fpaudit recheck --pins pins.json receipt-*.json \
  --rerun FlashProve/bin/cp_verify --files live2 --stored FlashProve/examples/accepted-proof

The receipts and pins are in receipts/; the files are FlashProve's examples/accepted-proof, with token 200 in place of 199 at position 2. Altered copies of these receipts give these results:

coin changed by one bit          FAIL coin
alarm dropped                    FAIL alarm
older beacon round swapped in    FAIL the beacon round is not seen + 2
record's token hash swapped      FAIL record digest
accepting transcript forged      OK offline · RERUN DISAGREES reject

The last line matters. An auditor can make up an accepting transcript, and an offline check of the receipt will pass it. Only re-running the verifier on the committed files catches the forgery. A receipt shows that the auditor's decision follows from what it recorded. It does not show that the auditor recorded the truth.

✗

a theorem about cp_verify · FlashProve's soundness theorem is about its Lean verify. The C++ link is a named hypothesis, [FP-chk-transport], with one lean-verify cross-check as evidence

✗

ordering proved offline · a historical drand round verifies as well as a fresh one. That the requester signed before the round came out rests on the requester's honesty, or on a timestamp witness we do not have

✗

a new statement · Rinberg et al. (2511.02620), eprint 2026/541 and covert security state commit-then-audit. What is new here is an instance whose decision is compiled from its own proof

✗

a served model · these are synthetic-weight proofs. Fresh proofs of a real model need an H100 and 330 GB of host memory

Why bother: sampling is how proof-carrying inference will actually be paid for. "We check 1%" means something only if the 1% can't be predicted, a missing answer counts as a failure, and the bound says what it costs. Here those three conditions are hypotheses of a checked theorem, and the code that enforces them is compiled from it.

Status, plainly: the Lean instance and its decision module are kernel-checked, with axioms pinned, on a minidregg lane branch. The auditor and the measurements are in breadstuffs. Two cross-model attack rounds (gpt-6-astra) were run and their findings repaired. The requester key in the live demo is held by the same process.
