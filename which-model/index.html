Everyone deserves verifiability · the missing half of proven inference

Which
model?

Zero-knowledge proofs of AI inference are arriving. They prove that a computation ran, faithfully, over committed weights. Read that sentence again, slowly · because it contains a hole big enough to serve you a different model through.

The hole.

A proof of inference certifies a relation over committed weights. It does not certify effort, and it does not certify a name. A provider can serve a small, cheap model, commit to its weights honestly, and emit entirely valid proofs · and the proof system has no opinion, because the proof was never about a named model. Only about whatever the prover committed to.

the missing piece was never a better proof.
it is a public name for the weights, bound to the commitment.

Call the attack what it is: a hollow model behind an honest proof. Closing it requires a public weight registry · an artifact an open project can ship and a closed one structurally cannot, because a closed provider cannot publish the very names its proofs would be checked against.

The registry, corrected.

The first registry fingerprinted published checkpoints by SHA-256 over their files. That is a checksum: it names bytes for a person with a downloader, and no proof system can open it. We said so at the time, and kept it as an integrity tool. Version 2 is the object a proof can meet: a root over the integers a prover actually commits, one leaf per row, one root per routed expert, so an opening of the experts that fired costs what fired.

One receipt.

FlashProve published a commitment to a public 4-bit conversion of Llama 4 Maverick (232 GB of GGUF files), ID c7982f8a…7c38. A commitment ID is a fingerprint of a randomised encoding, so it shares no preimage with anything we could compute. What links it to a name is a chain, and the receipt carries the chain:

E1

files: the five GGUF files' SHA-256, which FlashProve published. Checked on our stream: all five equal.

E2

files → integers: FlashProve's conversion rule, re-implemented and run over the whole 232 GB stream on a CPU. Our sums file has the SHA-256 FlashProve published for theirs, 689cd1d0…b519, byte for byte; over those integers we computed the registry v2 roots: 434 tensors, 3,072 routed experts, root set bf23bfb3…e830.

E3

files → commitment: FlashProve's committer with the published seed. Not recomputed by us: it needs an H100 and 330 GB of host memory. FlashProve published the result of their reproductions; the receipt says that is what vouches for this edge, and a verifier in strict mode refuses it until a recomputer it trusts signs it.

Around the chain sits a provenance graph · base model, quantization, integers, configuration, tokenizer, adapter, system prompt, tools · and an evaluation record signed over all of it, naming the deployment built from these integers. The verifier's accept decision is a Lean function, and the Lean theorem behind it says: if the receipt verifies and FlashProve's verifier accepts a proof against this ID, the proof's claim holds for the integers with this root set, inside the deployment the evaluation names · or FlashProve's verifier failed, or its binding broke, or SHA-256 collided on the file list. Nothing in between.

what it refuses, measured:
a real FlashProve proof that their verifier accepts (YES), presented against this receipt → REFUSE
Meta's published bf16 scores, properly signed, presented for the 4-bit commitment → REFUSE
25 altered receipts, including a colluding evaluator → REFUSE, every one

Re-run it: zkml-research/research/model_identity_receipt_2026_11_06/gates.sh streams nothing and checks G12-G16 in minutes; --sample re-fetches six tensors (one of them 3 GB) by range request and recomputes their roots. The full stream took 35 minutes on 14 CPU cores and kept no weights on disk.

What the receipt deliberately does not claim:

✗

that anyone evaluated this checkpoint · no lab has; the evaluation record on the published receipt is signed by a demonstration key and says so in its text

✗

that the 4-bit model behaves like Meta's bf16 model · two lossy conversions sit between them, and an evaluation does not cross either

✗

that the provider spent the computation of this model · the Hollow-LLM effort gap is a different problem; for published weights the root binding refuses ghost weights, for private weights there is no stranger to recompute it

Exactness is the boundary.

The second commitment of this pillar: bit-exact proving of the model's native format, with no acceptance windows. Every deployed fidelity-carrying system hands the prover a per-element tolerance · and there's a theorem (Or Zamir, February 2026) showing a functionally identical adversarial network can steer any target output through windows at floating-point rounding scale. Every bit of tolerance granted the prover is a bit an adversary can steer. A slack-free specification gives it nothing to hide in. Bit-exactness is not pedantry; it is the security boundary.

The cost curve is a choice.

We sorted every speedup this research measured by size. Statement-level and protocol-level levers · proving the smallest true statement, committing everything and auditing a random sample · are worth 10–100×. Prover-level levers are worth 2–4×. The field spends nearly all its effort on the second kind. The industry's cost curve is shaped by proving a statement nobody asked for · and that is the opening. The sampling-audit theorem is machine-checked now: commit everything, prove a sample, and any prover becomes deployable at bounded, quantified leakage.

The stance, for the record: everyone deserves verifiability. The point of doing this in the open is that verifiable inference should not be an enterprise feature. When we surveyed the best-known "open" zkML projects in August, most were not actually open-source · evaluation-only licenses, no-use-rights clauses, missing licenses. The open position is vacant. We intend to occupy it, in public, and we regard the teams publishing production numbers and stating their limitations plainly as collaborators in a worldsystem · competitors in no sense that matters here.

Status, plainly: one receipt exists for one real checkpoint, built from a full 232 GB stream on a CPU; its verifier's accept decision is a Lean function with a machine-checked statement of what acceptance means; two of its three edges are checked, the third rests on FlashProve's published reproduction until someone with an H100 recomputes it. No lab has signed an evaluation of it. The proving research is measurements and theorems, not a product. The far shore · training runs where the weights stay encrypted end to end · is named so you can watch us walk toward it.
