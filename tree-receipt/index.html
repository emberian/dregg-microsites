Initiative 12 · tree certificates

The record
is a tree

Every tool call an agent makes is a JSON record. Ask "does any Bash command contain pkill -f?" of the raw log and a string search answers the wrong question twice. Ask it of the canonical tree, one opened path per record, and the answer is a count with a certificate behind it.

Two ways a flat search is wrong

The log is 3,382 tool calls from one Claude Code session and its 72 helpers. A byte search of the 3,382 raw lines for pkill -f hits 47. Of those, 34 are not Bash commands at all: they are prompts handed to other agents, and files being written. And it misses a control we planted:

{"name":"Bash","input":{"command":"\u0070kill -f node"}}

JSON may spell p as \u0070. The tree certificate reads the decoded string at input.command, only on records whose name is Bash, so it catches the control and ignores the prompts.

The first answer is 13, not 0, and 13 is right: thirteen commands talk about pkill -f, and reading them, none invokes it (that reading is ours, not a theorem). Each count is a certificate over the same committed corpus (the Merkle Mountain Range of 3,382 record roots, 219ace22…4a61). A non-Bash record is refuted by opening its name; a Bash record opens its command. An opening also shows the keys of each object on the way down and a digest of every sibling value. The digests are unsalted, so a value you can guess (the name "Bash", a timeout of 120000) can be confirmed by hashing the guess. Unopened values are hidden only as well as they are hard to guess.

count = 0 means: for any records whose roots commit to this MMR root, none has name = "Bash" with a command this byte pattern accepts, or a hash collides at a pair the theorem names. It does not mean no agent ran pkill -f. The pattern skips `pkill -f x` substitutions, bash -c '…', aliases, and shell commands issued from other tools.

What the theorems say

The record is canonical. Values are deterministic CBOR (RFC 8949 §4.2.1): exact decimals, no floats, decoded strings, keys in one order, duplicate keys refused. The checker re-encodes what it reads and compares bytes; canon_injective says two trees never share a byte string, and the reader accepts only the one encoding of each tree. That two JSON spellings of one value parse to one tree is tested, not proved. (RFC 8785 JCS was the obvious alternative. It works on IEEE doubles, so a parser that converts 9007199254740993 to binary64 hands JCS the same number as 9007199254740992. JCS itself advises strings for numbers that need more precision.)

The opening tells the truth. walk_sound: an accepted opening reports the named record's real value at the path, or its real absence, or the hash collides at a pair computed from the record and the opening. Without the kind tag in each frame, [] and {} would share a digest; the falsifier is pinned.

The count is the count. corpus_count_mmr composes the openings with the MMR's own binding theorem: exactly count records match, or a hash collides at a computed pair. The MMR collision is lifted to SHAKE256 for short inputs; that the pair has that shape is not proved yet. Schemas compile to bottom-up tree automata (compile_correct), and a string leaf's check is the house DFA's accepting run.

Why bother: "grep says no" is two mistakes in a trench coat. A tree certificate counts the field you meant, reads the decoded string, opens one path per record, and is checked by a program whose meaning is a theorem.

Status, plainly: the Lean statements are kernel-checked and audited by a second model; the verifier is the extracted Lean checker, on SHAKE256 standing in for the deployed cSHAKE256. The full certificates disclose every Bash command of the session and are not published. There is no proof-system leg yet.
